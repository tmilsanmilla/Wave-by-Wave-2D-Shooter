# Pixel Pulse shared sign-in

Outpost Zero is an OIDC consumer of `https://pixel-pulse-websites.vercel.app/api/sso`, client `outpost-zero`. The exact callback is `https://wave-by-wave-2-d-shooter.vercel.app/api/pixel-pulse/callback`. Passwords are entered only on Pixel Pulse, never exchanged or duplicated. No central admin roles are imported.

Existing players choose **Link existing account · Highly recommended**, sign into the game once, and are then taken to Pixel Pulse. The same option is in Account Settings and the first-username screen. The server validates their current signed Neon token before recording the link attempt. The callback requires both this ownership proof and the verified central identity; matching email/username alone never grants existing game data. The game UUID, inventory, ranks, friends, messages, bans, and permissions stay in place. Both accounts must have the same email. The central username must be available locally. A proved link adopts that one name immediately; ordinary game-only renames still have the 21-day limit, and linked clients cannot rename independently.

New players choose **Continue with Pixel Pulse** to create the game account using their verified central email and canonical username. Already signed into Pixel Pulse? The top-level redirect reuses its managed login cookie, without a forced password prompt. Expired/absent sessions still require sign-in; missing usernames still require one explicit shared-name choice. Cookies remain host-only: the game never reads Pixel's cookie or password. A duplicate local email offers the recommended proof-based linking flow, not an automatic merge. Username/email are refreshed on subsequent shared sign-ins. A changed central email requires an explicit account-ownership update rather than silently moving email-based permissions.

The hub launch URLs are `https://wave-by-wave-2-d-shooter.vercel.app/?pixel=link` and `https://wave-by-wave-2-d-shooter.vercel.app/?pixel=create`. Link opens the game credential form and waits for native ownership proof; Create launches Pixel authorization directly. These non-secret intents are consumed on load, canceled by Cancel/Guest and never persisted with credentials. A signed-in game account uses proof-based linking even from Create, so existing progress is not silently replaced.

The maintained `openid-client` checks issuer, exact redirect, state, PKCE S256, nonce, audience, expiry, signatures and matching UserInfo subject. Attempt records are cookie-bound, expire after five minutes and are deleted atomically before exchange. Cookies are host-only, Secure, HttpOnly and SameSite=Lax. Only SHA-256 session-token hashes are stored in private, forced-RLS tables; no passwords or OAuth tokens are persisted.

Local game sessions last seven days. The game issues 120-second database tokens from a server-only RSA key. They explicitly name this game's two verifier audiences: the native Neon Auth origin and `outpost-zero-pixel-pulse`. Both verifier layers still check their expected audience; signatures, roles and RLS are not bypassed. The public `/api/pixel-pulse/database-keys` endpoint includes only the game's managed-Neon public keys and its dedicated game public key, never Pixel Pulse's signing key. A separate branch-scoped JWKS registration adds these keys without replacing native Managed Auth. Database access remains the existing `authenticated` role with the existing game RLS and ban checks. Signing out removes the server session; already issued tokens expire within two minutes. Signing out of Pixel Pulse alone does not sign out every connected site's local session.

Apply `neon/migrations/002-pixel-pulse-sign-in.sql` directly to the correct Neon game branch. It only adds three private tables, a username guard, and a self-only username lookup; `oz_identity.game_user_id()` also resolves the explicitly namespaced `pixelpulse:<subject>` identity. Never expose `oz_identity` in the Data API.

Then apply `003-pixel-pulse-canonical-name.sql`. It changes only the username-clock function: a canonical name from the private server-owned link registry may be adopted immediately; all other names keep the previous cooldown. No account, progress, session or role is deleted.

Server environment: existing `DATABASE_URL`; `PIXEL_PULSE_GAME_SIGNING_KEY` (private RSA JWK JSON, unique `kid`, never public); and `PIXEL_PULSE_GAME_ENABLED=true` **only after** provider discovery/client registration and game JWKS trust are verified. Publish only the public key at `/api/pixel-pulse/jwks`. Disabling the flag hides new connections but preserves existing sessions and native game login. Do not delete or replace existing Neon/Supabase JWKS registrations.

No changes to the Supabase rollback copy are required.
